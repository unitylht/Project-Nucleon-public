# Nucleon Lab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A third, isolated deployment at `/lab/` where a Pydantic AI agent and an assistant-ui front end work the same fictional business through Nucleon's new business tool layer, which is also exposed as an MCP server; validated by tests, scripted conversations and the builder's own browser sessions, and compared with the preview.

**Architecture:** The records server (`prototype/server.py`, stdlib) gains a framework-neutral tool surface (`GET /api/tools`, `POST /api/tools/<name>`) over its existing `DeskTools`, plus the operations the review showed missing. A new `lab/` package (Starlette + uvicorn + Pydantic AI, in its own venv) serves the chat UI, keeps its own conversation store, runs the agent whose tools call the records surface with the person's session cookie, and mounts an MCP server over the same operations. The UI is a Vite build of assistant-ui served as static files.

**Tech Stack:** Python 3.12.14 (`~/srv/nucleon/runtime/python-3.12.14/bin/python3` to create venvs), `pydantic-ai-slim[openai]==2.58.0`, `mcp==2.3.0`, `starlette`, `uvicorn`, `httpx` (all already resolved in the spike venv); Node 24 for the Vite build only; `@assistant-ui/react` 0.15.x, React 18/19, Vite; Playwright (`NODE_PATH=/Users/jason/Documents/aiRP/tests/ui/node_modules`); SQLite.

**Spec:** `docs/superpowers/specs/2026-10-21-nucleon-lab-design.md` (§3 decision, §5 constraints, §7 builder's calls). Research notes are scratch, not records.

## Global Constraints

- Fictional data only; no access codes, cookies, tokens or private ledgers in git; `lab/config.example.json` holds placeholders only.
- The records server stays stdlib-only; all new dependencies live in `lab/requirements.txt` (pinned) and the Lab venv.
- Relative URLs everywhere (the Lab is served under `/lab/`; the records instance under `/lab/records/`); the UI must work at 375/390 px; Arial; no inline styles.
- Existing tests and checks keep passing: unit suite 428 → grows, `desk_check` 73/73, `layout_check --seed` 217/217, `ui_check` 150/150, `conversation_check` mock 310/310.
- Write-capable checks run only on scratch servers (`deploy/scratch_only.js`); never on ports 8620, 8621, 8622, 8623 or their logs.
- Business boundaries are enforced in the operations layer: the owner alone confirms (and only through `decide`); staff never receive owner-only lines, suggestions, day limits from unshared guidance, or prepared decisions; every figure in a result is computed by code; nothing leaves Nucleon.
- Prompts in `lab/prompts.py` are recorded verbatim in PROMPTS.md as `lab-v0.1`, printed by `python -m lab --print-prompts`.
- Commit after each task; never push or deploy from an implementer; commit messages end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` unless the harness gives another line.

## Review Focus

1. A staff call to `POST /api/tools/caseDetails` for a case whose owner wrote "Up to 14 days this time" must return no day limit, no suggestion and no prepared decision; the owner's call returns all three. (Task 1 test.)
2. `compareExtension` never writes: calling it twice changes no request, event or preparation; `withdrawPreparation` clears only the named version and records `decision.withdrawn`. (Task 1 test.)
3. The Lab's SSE endpoint rebuilds history from its store for the session's role and ignores any `messages` the client sends; an owner turn is never streamed to a staff session. (Task 2 test.)
4. The claim validator: a reply saying "I have prepared/approved/declined/withdrawn/recorded …" with no matching tool call in this run is retried once and then replaced by the fixed sentence; a decision can never be committed through the agent (no tool calls `decide`). (Task 2 test.)
5. The Confirm button in the UI posts to the records API with `preparedVersion`; a stale version shows the 409 message and no decision is recorded. (Task 3 test + Task 6 browser check.)

**Interfaces:**
- Produces `GET /api/tools` → `{"tools": [{"name", "kind", "needsConfirmation", "description", "parameters": <JSON schema>}]}` for the caller's role after overrides (403 without a session).
- Produces `POST /api/tools/<name>` with body `{"args": {...}, "message": "<the person's message, optional>"}` → `200 {"ok": true, "result": {...}}` or `200 {"ok": false, "error": "<CODE>", "message": "..."}` for tool-level refusals (`FORBIDDEN`, `INVALID_ARGUMENT`, `NOT_FOUND`, `AMBIGUOUS`, `MISSING`), 403 for a tool the role may not call, 404 for an unknown tool. `message` is what `_prepareDecision` grounds days/dates against. Model-calling tools (`interpretStatement`) are executed too (they call the adapter; a mock server answers with its rules).
- Every result carries `"subject": {"customerId", "name"} | null` and, where dates occur, `<field>Text` beside the ISO field (reuse `dated()`).
- `compareExtension(requestId|'current', days?|date?)` → `{requestId, invoiceReference, currentDue, currentDueText, proposedDate, proposedDateText, daysFromDue, askedDate, askedDateText, askedDays, limitDays|null, latestWithinLimit|null, latestWithinLimitText|null, withinLimit|null, subject}`; staff get `limitDays: null` unless the limit comes from a shared line; neither days nor date → `MISSING`.
- `withdrawPreparation(requestId|'current', version?)` (owner) → `{withdrawn: true, version}`; no preparation → `{withdrawn: false, note: 'Nothing was prepared.'}`; a version that is not current → `STALE`; event `decision.withdrawn`.
- `workQueue()` → `{forYou: [{requestId, invoiceReference, customer: {customerId, name}, status, statusLabel, waitingOn: 'owner'|'staff'|'none', why, askedDateText, link}], waitingOnOthers: [...same...], asOf}`; owner's `forYou` = cases awaiting the owner (plus open questions for the owner); staff's `forYou` = cases with open staff questions or drafts; the other list is what waits on the other role.
- `listRequests(customerId|invoiceReference|'current', status: 'open'|'decided'|'all' = 'open')` → `{requests: [...], subject}` using the `summary(r)` shape plus `waitingOn`.
- `prepareHoldingMessage(requestId|'current')` → `{text, status, subject}`: a code-templated, promise-free sentence pair naming the invoice, the status ("your request is with the owner; we will confirm once it is decided") and the current due date; no amounts unless exact.
- Registry kinds: `compareExtension` read/calculate, `withdrawPreparation` act (internal, no confirmation), `workQueue` read, `listRequests` read, `prepareHoldingMessage` prepare (no confirmation; the person copies it).

**Interfaces:**
- Consumes Task 1's `GET /api/tools` and `POST /api/tools/<name>`; the records instance's `GET /api/session` (role) and `POST /api/session` (sign-in, done by the browser directly).
- Produces `Deps(role, cookie, thread, focus)`; `LabReply` = the agent's final text (plain `str` output; `detail` is chosen by code: `summary` when the reply has at most two figure-bearing sentences, else `full`).
- Produces the Lab HTTP API (all under the app root; the UI calls them relatively): `GET api/session` → `{role, workspace, version}` (proxied from records; 401 without a valid cookie); `GET api/threads` → `[{id, kind, requestId, title, lastTurnAt}]` (general thread first; case threads come from `listRequests('all')` so every case has one); `GET api/threads/{id}` → `{thread, turns: [turns this role may see]}`; `POST api/threads/{id}/chat` body `{text}` → `text/event-stream` with events `turn {seq, role}` (the stored person turn), `delta {text}`, `tool {name, args}`, `result {name, ok, result}`, `card {kind, data}` (one per tool result that has a UI: overview, case, queue, compare, prepared, draft, holding, navigation, context), `reply {seq, text, detail, withheld, subject}` (the stored agent turn), `error {message}`; `POST api/threads/{id}/focus {customerId|null}` as the desk has; `GET api/tools` (the registry for the role, passthrough).
- Visibility: owner turns are stored `visibility 'owner'`; staff turns `'all'`; the model's history is rebuilt from the store for the session's role (last 12 turns), never from the request body.
- Validators (`lab/guard.py`, each raising `ModelRetry` with the exact reason, `retries={'output': 1}`): `no_false_claims` (claims of prepared/approved/declined/withdrawn/recorded/decided/added/created with no matching tool call this run; `decided`/`recorded` always refused); `figures_from_results` (every digit run and every date in the reply appears in a tool result of this run or in the person's message); `amounts_marked` (an amount within 60 characters of one of `exact`, `stated as of`, `at most`, `as recorded`); `no_credit_judgement` (reuse the coordinator's `CREDIT_JUDGEMENT` pattern, with the quoted-known-line exemption); `staff_no_private_hint` for staff (reuse the coordinator's pattern and rewrite rule). After the retry fails, the stored reply is "Here is what the records show[ about <subject>]." with `withheld` = the reason kind, and the cards still shown.
- Limits: `UsageLimits(request_limit=8)`, run timeout 120 s, `ModelSettings(temperature=0)`; OpenAI client retries 0 (the gateway queues).
- `LAB_SYSTEM` (in `lab/prompts.py`, verbatim in PROMPTS.md): who the person is and what the agent may do per role; discuss what is on screen; use `compareExtension` to compare, `prepareDecision` only when asked to prepare/approve/decline, `withdrawPreparation` to cancel a preparation ("not a decline"); quote figures and dates exactly as the results' `…Text` fields write them; the person's own numbers may be repeated; never total amounts; every amount with its mark; base "what next" on `workQueue`/`nextSteps`; answer every part of a multi-part ask; when a tool is not available, say so plainly.
