# Nucleon Lab, second iteration: coherent revisions, concise presentation, understandable state (design, 21 October 2026)

Status: design for the next Lab deployment on branch `explore/agent-coordinator-20261019`. The root site (`f95f50f`) and the preview (`df10ab6`) stay unchanged. Builds on `docs/superpowers/specs/2026-10-21-nucleon-lab-design.md`.

## 1. Intent

The independent review confirmed the Lab's gains (cross-customer queues, holding language, comparison without preparation, conversational preparation, withdrawal that is not a decline) and found three things that make it hard to trust through a conversation: a revision lost information the owner asked to keep and left stale Confirm buttons; every retrieval is shown as a card and then repeated in prose; business state and navigation are unclear (an approved case still labelled with its old due date; two requests with the same sidebar label). The team's direction: a natural assistant that stays understandable and dependable when the person changes their mind.

## 2. Causes established (from the Lab's store and the records)

- **Reason lost on revision.** The model passed the retained reason on the second `prepareDecision` call; the records' grounding rule accepts a reason only if it appears in the current message, and "Keep the same reason" contains no reason text, so the reason became "No reason given; prepared on the desk." A revision has no notion of "keep what I did not change".
- **Stale Confirm buttons.** Each prepared card renders from the tool result stored with its turn. Nothing ties a card to the live state, so superseded and withdrawn preparations keep a button. The server refuses a stale `preparedVersion` (409), which is why nothing wrong was committed, but the person cannot see that.
- **Invented explanation.** `caseDetails` carries only the active preparation, so the agent had no history to explain the earlier card from and made one up (the claim guard does not cover explanations of the UI).
- **"Current due date" after approval.** The case shape has one `currentDue` (the invoice's recorded due date). After a decision the effective date is the approved one, but nothing names it.
- **Identical sidebar labels.** Thread titles are "reference · customer" only; two requests on the same invoice look the same. Intake has no duplicate check.
- **Duplicated cards and prose.** The UI shows every tool result as an open card and the model restates it; tool names ("findCustomers: done") are shown as progress.

## 3. Decisions

1. **Revision lifecycle in the records.** A preparation is a versioned proposal with a status: `current`, `superseded` (replaced by a later version), `withdrawn`, `confirmed`. The request keeps `preparations` (the history) and `preparedDecision` (the current one or none). A new `prepareDecision` while one is current is a revision: fields not supplied keep the current values (outcome, days/date, reason), the reason is accepted if it is in the person's message **or equals the current preparation's reason** (an explicit "keep the same reason" is honoured by the agent passing it through), and the previous version becomes `superseded`. `withdrawPreparation` marks `withdrawn`; `decide` with the current version marks `confirmed`. Every status change is an event. `caseDetails` returns the history with statuses and the active version; the situation prelude shows it to the agent, so explanations come from state.
2. **One proposal component, live state.** The UI renders every prepared card from the case's live `preparations` by version: `current` shows the Confirm button; `superseded by version N`, `withdrawn`, `confirmed (decided …)` show a status line and no button. The state is fetched when a thread opens and after every turn, so navigation and refresh show the same thing. The server still refuses stale versions (verified in isolated data).
3. **Presentation: prose first, records behind a disclosure.** An assistant message is its prose. Tool results are folded under one "Records (N)" disclosure per message, closed by default. Exceptions, decided by code from the reply's `detail` and the kinds of result: when the reply is `full` (the person asked to see or list records), the one primary block is shown open; an action card (prepared decision, draft customer, holding message, understood statement) is shown open as the one current action card; a comparison card is shown open when the turn's tools were only `compareExtension`. Tool activity ("findCustomers: done") moves to an "Activity" inspection toggle, closed by default; while a run is in progress the message shows one human line per step ("Finding the customer…", "Reading the case…", "Comparing dates…", "Preparing the decision…", "Thinking…"). The prompt asks for one or two sentences when a card carries the figures; the figures still pass the validators.
4. **Understandable business state.** The case shape gains `originalDue` (recorded on the invoice at request time), `dueNow` (the approved date once decided, else the original) and their text forms; the case card and the prelude show "Due now" and, when they differ, "Originally due". Thread titles become "DEMO-101 · Harbour Demo Supplies · With the owner · asked Thu 10 Dec" with the status label and asked date, and a second open request on the same invoice is marked "(2nd request)". `openRequest` flags a likely duplicate (same invoice, same asked date, an open case) in its result and in the case's `flags`, without merging or refusing. A case thread opens with a header: reference, customer, status, due now, asked date, amount with mark.
5. **Tony's ideas, scoped.** Adopted now: (a) *check whether earlier knowledge still holds*: when a case cites a line that is an expectation about the future or is older than 30 days, the brief gets a code-generated question for the owner ("On <date> you said '<quote>'. Does that still hold for this request?") with `from: 'code'`; answering records a fresh line scoped to the case, declining retires nothing; (b) *staff raise a concern*: a `raiseConcern(requestId, text)` operation for staff that stores a case line visible to the owner and puts the case in the owner's queue with the reason "staff raised a concern"; (c) *owner involvement explicit*: already the queue's "waiting on owner". Kept separate on purpose: a one-off approval is a decision on one case; reusable guidance is a confirmed line with a scope the owner stated; a credit-limit or new-order rule is out of scope and is not inferred from an extension approval. Needing team clarification: whether a yes on one case may apply "from now on" and for how long; the reasons-skipped path in the form; the question set for A08. Future: automatic decisions on standing authority (not built), periodic relationship reviews (not wanted as a questionnaire).

## 4. Non-goals and anti-goals

Non-goals: changing the preview or the desk's UI; merging or deleting duplicate requests; standing-authority automation. Anti-goals: phrase-specific guards for the reviewer's sentences; forcing extra tool calls as a fix for presentation; hiding the action card behind a disclosure; any owner-only item reaching staff through the history or the header.

## 5. Builder's calls

The history is stored on the request (`preparations`) rather than reconstructed from events, so one read gives the UI and the agent the same picture. The duplicate-intake flag is informational only. The "still holds?" question is generated by code in the records' needs step, after the model's questions, and deduplicated per line. The progress lines are a fixed map from tool name to a human phrase in the UI, not model text.

## 6. Validation

Unit tests in the records for the lifecycle and the new fields; Lab tests for the prelude and tools; `lab_check` for live-state cards after navigation and refresh and for a stale Confirm (409, nothing recorded); scenarios for the reviewer's DEMO-201 sequence and the presentation defaults; the builder's own browser conversation (comparison → preparation → revision keeping the reason → withdrawal → re-preparation → confirm; unfamiliar wording; an explanatory follow-up; a customer switch) with screenshots read, not only DOM assertions.
